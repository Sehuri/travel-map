# 手记置顶：实现与配置

日期：2026-11-17。开发完成，待独立测试会话验收；未执行线上迁移或发布。

## 配置顺序

本功能需要服务端展示元数据，前端不会用浏览器缓存模拟全站置顶。

1. 测试会话先在隔离本地数据库中加载已有 `supabase/place_journals.sql`，再加载 `supabase/journal_pinning.sql` 并验收权限、事务与 UI。
2. 获得用户当次线上配置授权后，在**已经配置好手记的 Supabase 项目**执行 `supabase/journal_pinning.sql`。等价迁移为 `supabase/migrations/20261117000000_journal_pinning.sql`，两者保持逐字一致，按现有部署方式选一份执行。
3. 已上线环境只执行增量置顶 SQL，**不要为此重新执行旧的手记初始化 SQL**。旧初始化投影没有新增字段，重新运行不属于增量升级流程。
4. 迁移成功后，由测试会话按授权推送前端并验证真实站主与匿名访问。若用户尚未授权迁移，必须报告线上配置待完成，不能靠本地回退或忽略错误声称功能上线。

迁移事务没有生产种子，不替真实手记设置置顶，也不改存储、媒体权限、旧版本读取或公共投票。旧前端忽略新增字段仍可读公开列表；新前端在缺少 RPC 时向主人明确提示配置未完成，普通阅读不受阻。

## 元数据和时间边界

在 `journal_entries` 上新增：

- `pinned_at timestamptz`：为空未置顶；新置顶使用服务端 `clock_timestamp()`；取消为空。
- `presentation_revision bigint not null default 0`：展示状态的并发版本，独立于正文 `revision`。
- `presentation_undo jsonb`：仅保留当前最后一次展示操作的回执，包括操作 UUID、撤销 UUID 与之前的置顶时间。不是全量日志，不保存内容或照片。

公开视图沿用原有列和顺序，末尾仅追加有效 `pinned_at`，不公开展示版本或回执。公开状态仍要求 `published + public + published_version_id`，不会因有置顶字段扩大读取范围。

置顶/取消/撤销只改上述展示字段；不修改正文 `revision`、管理 `updated_at`、`published_at`、公开投影 `updated_at`、到访日期、正文 JSON、草稿或内容版本。

`journal_clear_ineligible_pin` BEFORE UPDATE 触发器与原有撤下、归档、私人发布处于同一事务：退出正式公开状态时清空置顶及回执、增加展示版本。即使原来未置顶也增加展示版本，避免旧请求跨“撤下再公开”周期生效。公开更新发布仍公开时保留置顶时间；仅保存私人修订不会撤下现有公开版。恢复/重新公开不自动恢复置顶。

## RPC 与授权

三个 RPC 都复用 `is_current_user_owner()`，校验 `auth.uid()` 和条目归属。匿名无执行权限；登录非主人也会被函数拒绝。没有放开表 UPDATE 权限。

| RPC | 参数 | 行为 |
| --- | --- | --- |
| `journal_pin_status` | `p_id` | 主人读取当前正式状态、置顶时间、展示版本和最新回执标识；不返回标题、正文或私人媒体 |
| `journal_set_pin` | `p_id,p_pinned,p_presentation_revision,p_operation_id` | 锁行，校验正式公开状态与展示版本；同一目标已经达成则不更新；同一操作 UUID 重试不刷新时间 |
| `journal_restore_pin` | `p_id,p_presentation_revision,p_undo_token,p_operation_id` | 仅能恢复当前有效回执中的旧状态/旧时间；检查版本和撤销令牌，不能任意传入时间覆盖其他操作 |

回执中的旧时间由服务端保存，UI 只持有令牌；撤销取消置顶会恢复原时间和相对位置。撤销成功本身也记录操作 UUID，以便响应丢失后幂等核对。下一次实际展示修改或退出公开都会使旧撤销失效。

UI 提供约 8 秒空闲撤销窗口，悬停/焦点暂停计时。服务端回执没有固定 8 秒到期时间，以支持悬停/键盘停留；它只在最新展示状态下有效，不能越过并发修改、撤下或归档。这不是公开可读或可匿名使用的凭据。

错误码 `40001` 表示状态/并发冲突；`42501` 表示权限不足；参数错误 `22023`。缺少配置时可能收到 `PGRST202` / `42883` 等，前端给出配置提示。

## 前端行为

- `journal-pinning-engine.js` 是**公开网格专用**排序层：先复用现有过滤和三种普通排序，再置顶优先、置顶组按时间/ID 排列；不改 `JOURNAL_ENGINE.filter()` 或更新面板引擎。我的记录保持原顺序。
- 所有访客看到角标；主人卡片增加独立“更多操作”按钮，位于图片链接外。桌面锚定按钮列表，手机底部 native dialog，使用现有 Heroicons。非公开条目只能编辑，置顶项禁用并说明原因。
- 操作先读取服务端展示版本，成功后再改角标/顺序。列表缓存卡片及媒体元数据，展示重排复用节点/照片；若服务端当前内容版本已经变化，则重新读取完整授权列表。
- 重排尽量锚定另一条可见卡片；不强制滚到页首。原条目移出视口时焦点转可见反馈；用户已在输入其他筛选时不主动抢走焦点。
- 置顶写入等待 12 秒，状态核对等待 10 秒；超时或网络错误视为结果不明。先只读核对操作 UUID；未确认时允许继续核对，或手动用**相同操作 UUID、原版本/令牌**安全重试原操作，不用新 UUID 盲目重复置顶。
- 同一条目未确认时阻止新展示操作。关闭菜单仍可用，晚到响应按任务身份处理，不把过滤掉的记录重新插回当前范围。没有轮询服务；跨设备在刷新/重新读取后使用服务器结果。
- 仅公开列表出现“置顶优先，其余按…排序”。置顶不增加手记篇数、地点数、城市数、照片数或百城进度。
